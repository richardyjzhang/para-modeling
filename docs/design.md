# 总体设计

> 本文档是项目设计的权威版本。设计发生变化时，先改这里，再动代码。
> 最后更新：2026-09-14（第 7 期：选中与联动）

## 1. 项目定位

Web 端**通用参数化建模工具**，偏向工程场景（桥梁、房建等）。核心机制借鉴 AVEVA PDMS 的元件库（Catalogue）：

- 元件不是死网格，而是**参数 + 基本图元组合**的模板，实例化时代入参数值动态生成几何；
- 元件带 **P-points（连接点/局部坐标原点）**，用于实例间的定位与拼接；
- 工程模型是一棵**层级树**（类似 PDMS 的 WORL > SITE > ZONE > 实例），实例挂在树上。

主要输出是**三维可视化展示**。不做管线路由，不做 CAD 数据交换（STEP/IGES），不做 CAE。

### 两大业务模块

1. **元件库维护模块**：元件分类管理 + 元件编辑器（定义参数、组合图元、写表达式、定义 P-points、实时预览）。
2. **工程建模模块**：项目管理 + 模型层级树 + 3D 场景（实例化元件 / 摆放裸图元、填参数、移动旋转、P-point 对齐）。

## 2. 技术架构

- **前端**：Vue 3 + TypeScript + Vite + Three.js + Tailwind CSS + math.js
- **后端**：Python + Flask + SQLite，REST API
- **职责分界**：后端是纯持久化层（模板、项目、参数值），**几何一律由前端按"模板 + 参数"现算**。渲染管线：

```
模板 JSON + 参数值
  → 表达式求值（math.js）
  → 递归展开嵌套引用（bindings 传参）
  → 纯图元树（每个图元的尺寸/位置/朝向都是具体数字）
  → Three.js BufferGeometry / Mesh
```

## 3. 元件模板数据结构

模板 = **参数列表 + 零件列表（items）+ P-points**。零件要么是基本图元（`primitive`），要么是对另一个模板的引用（`ref`）。所有尺寸、位置、旋转都是**表达式字符串**（哪怕是常数也写成 `"300"`）。

### 3.1 示例：门把手（纯图元模板）

```json
{
  "id": "tpl_handle",
  "name": "门把手",
  "params": [
    { "name": "L", "type": "number", "default": 120, "min": 50, "max": 500, "desc": "把手长度" },
    { "name": "D", "type": "number", "default": 20, "desc": "杆径" }
  ],
  "items": [
    {
      "kind": "primitive",
      "shape": "cylinder",
      "name": "横杆",
      "dims": { "radius": "D / 2", "height": "L" },
      "transform": { "pos": ["0", "0", "0"], "rot": ["0", "90", "0"] }
    },
    {
      "kind": "primitive",
      "shape": "cylinder",
      "name": "立柱",
      "dims": { "radius": "D / 2", "height": "60" },
      "transform": { "pos": ["-L / 2", "0", "0"], "rot": ["0", "0", "0"] }
    }
  ],
  "ppoints": [
    { "name": "P1", "pos": ["-L / 2", "0", "-60"], "dir": ["0", "0", "-1"], "desc": "安装点" }
  ]
}
```

### 3.2 示例：门（嵌套引用门把手）

```json
{
  "id": "tpl_door",
  "name": "带把手的门",
  "params": [
    { "name": "W", "type": "number", "default": 900 },
    { "name": "H", "type": "number", "default": 2100 },
    { "name": "handleLen", "type": "number", "default": 120 }
  ],
  "items": [
    {
      "kind": "primitive",
      "shape": "box",
      "name": "门板",
      "dims": { "x": "W", "y": "40", "z": "H" },
      "transform": { "pos": ["0", "0", "H / 2"], "rot": ["0", "0", "0"] }
    },
    {
      "kind": "ref",
      "templateId": "tpl_handle",
      "name": "把手",
      "bindings": { "L": "handleLen", "D": "18" },
      "transform": { "pos": ["W / 2 - 60", "25", "1000"], "rot": ["0", "0", "0"] }
    }
  ],
  "ppoints": []
}
```

用户既可以直接实例化 `tpl_handle`，也可以实例化 `tpl_door`（内部自动摆好把手），还可以新建模板引用 `tpl_handle` 做自己的门。

### 3.3 嵌套规则

- 表达式**只能引用本模板自己的参数**；跨层传参只通过 `ref` 的 `bindings`（键 = 子模板参数名，值 = 父模板上下文中的表达式）。
- **禁止循环引用**：保存模板时后端沿依赖关系表做依赖图检查，成环则拒绝保存。
- **活引用**：引用始终指向被引模板的最新版本，改了门把手，所有用它的门都跟着变。版本固定（pin）暂不做。

### 3.4 图元集合

| 阶段 | 图元 | 说明 |
|---|---|---|
| 基础 | box / cylinder / cone(棱台圆台) / sphere / torus | 对应 PDMS 的 BOX/CYLI/SNOU/CTOR 等 |
| 扩充一 | extrusion（拉伸体）/ revolution（旋转体） | 2D 轮廓（多段线，先用坐标表格输入）沿直线拉伸 / 绕轴旋转 |
| 扩充二 | sweep（扫掠体） | 2D 截面沿路径（直线/圆弧）扫掠；进阶：首尾截面渐变（放样） |

各图元的 `dims` 结构互不相同（异构），这是模板定义整体存 JSON 的原因之一。每个图元的参数含义、局部坐标系、与 Three.js 默认几何的差异见 [`docs/primitives.md`](primitives.md)。

### 3.5 P-points

每个 P-point = 名称 + 位置（3 个表达式）+ 方向（3 个表达式，单位向量）。用途：

- 元件编辑器中可视化显示（小箭头）；
- 工程建模中"对齐吸附"：把实例 A 的 P-point 对到实例 B 的 P-point 上（位置重合、方向对接）。

## 4. 表达式引擎

### 4.1 能力范围

- 运算：`+ - * / ^`（乘方）、一元负号、括号
- 函数白名单：`sqrt, sin, cos, tan, asin, acos, atan, atan2, abs, min, max, floor, ceil, round`
- 三角函数按**角度制**约定（工程习惯），实现层统一换算
- 操作数：数字字面量、本模板参数名

### 4.2 实现方案（决策）

- **前端**：math.js 负责解析与求值；解析后遍历其 AST，只放行白名单节点类型与白名单函数，拒绝 math.js 的多余能力（矩阵、字符串、单位等）。报错带字符位置。
- **后端**：Python 标准库 `ast.parse` 解析 + 相同白名单节点检查，**只校验合法性，不求值**（后端从不算几何）。用于保存/导入模板时把关数据质量。
- 语法差异统一约定：**用户写 `^` 表示乘方**；后端校验前做 `^` → `**` 的预处理。

**为什么不自写解析器**：语法收敛、打包体积无所谓（Three.js 本来就大）、math.js 久经考验免维护；自写唯一优势是报错更精细，不值得付出正确性风险和测试成本。
**为什么不用 eval**：安全 + 无法做白名单控制 + 报错不可控。

## 5. 存储设计原则（SQLite）

> 本节只定原则。具体表结构在实现过程中逐渐沉淀到 `docs/schema.sql`，以该文件为准。结构变更由用户手动对数据库执行 SQL，后端启动时不自动建表或迁移。

- **需要查询/索引的拆列，纯内容整体存 JSON 文本。** 编辑时模型在前端内存里，后端只是持久化层，SQLite 足够。
- **元件模板内部定义（图元、表达式、P-points）整体存一个 JSON 字段。** 理由：编辑器总是整读整写；图元结构异构且会持续扩充，拆表会导致频繁改表结构。
- **两处冗余投影必须拆表**（保存模板时由后端解析 definition 重建）：
  - 参数列表 —— 供元件列表页展示参数、实例化时校验，不必解析整个 definition；
  - 模板间依赖关系 —— 供循环引用检测和"哪些元件用了我"反查。
- **工程模型层级树用结构化邻接表**（节点表 + `parent_id`），不用 JSON 表达层级。树操作（移动子树、按模板反查实例）是真实高频查询。
- **模型树节点三种类型**：`group`（组织层级，类似 PDMS 的 SITE/ZONE）、`primitive`（裸图元直接摆进场景，PDMS 里 EQUI 下也能直接挂 BOX/CYLI，同理）、`instance`（元件实例，只存模板引用 + 参数值，**不存几何**）。父节点必须是 `group`（根级 `parent_id` 为 null）。
- **分组带可编辑 transform，子节点存相对父级的局部坐标。** 渲染时每个 group 施加自身 pos/rot，移动/旋转分组带动整棵子树。
- **工程侧永远只存参数值，不存几何结果。** 元件模板改动后，所有实例下次渲染自动反映新形状（活引用）。

## 6. 导入导出

- 导出：选中若干模板 → 后端收集其全部传递依赖 → 打包成一个 JSON 文件（含所有模板 definition + 分类信息）。
- 导入：解包 → 逐个校验（表达式白名单、依赖完整性、循环检测）→ id 冲突时提示覆盖或跳过 → 重建冗余表。
- 对标 PDMS 元件库导出 TXT 的玩法，但直接用 JSON。

## 7. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| 1 | 几何只在前端算，后端不碰几何 | 参数化的本质是存参数；避免后端几何内核的复杂度；输出只是可视化 |
| 2 | 模板内部定义整存 JSON，参数/依赖冗余拆表 | 编辑器整读整写；图元结构异构且会扩充；拆表只为列表页与循环检测这两个真实查询场景 |
| 3 | 工程层级树用结构化邻接表 | 树操作（移动子树、按模板反查实例）是真实高频查询 |
| 4 | 表达式用 math.js + AST 白名单，后端 ast 校验不求值 | 见 4.2 |
| 5 | 嵌套用 ref + bindings，活引用，禁循环 | 行为符合直觉，实现简单；版本 pin 留待有真实需求 |
| 6 | 尺寸从第一天就存表达式字符串 | 参数化阶段（第 8 期）零返工，只换求值器 |
| 7 | 纵切分期（每期都是可用产品） | 用户要随时能上手、随时看得懂；横切分层要到最后才能用 |
| 8 | 暂不做：性能优化、多用户权限、Spec 等级库、版本 pin、管线路由 | 控制范围 |
| 9 | Z-up 适配：只改 `camera.up = (0,0,1)`，并把 `GridHelper` 绕 X 转 90° 落到 XY；不做全局坐标变换 | Three.js 默认 Y-up，工程约定 Z-up；改相机 up 后 OrbitControls 与坐标轴（蓝=Z）自然朝上，后续图元可直接按 Z-up 摆放 |
| 10 | 分组带 transform，子节点存相对父级的局部坐标；渲染用 THREE.Group 嵌套 | 移动分组要带动子树；与 Three 场景图同构，实现直观 |
| 11 | 点选用 Raycaster + 点击位移阈值区分拖拽；高亮用 OutlinePass 深橙轮廓（EffectComposer + MSAA/SMAA）；选中分组时高亮整棵子树 | 不改 mesh 材质，球体/圆环等无硬边图元也能描边；深橙在浅色背景上比亮橙/蓝色更清楚；切后处理后面的 MSAA 失效，需在 Composer 目标上补抗锯齿 |
